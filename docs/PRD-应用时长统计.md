# PRD · 应用使用时长统计

| 项 | 内容 |
|----|------|
| 版本 | v1.0 |
| 日期 | 2026-08-05 |
| 状态 | 待评审 |
| 关联项目 | dailylog · 今日轨迹 |

## 1. 背景与目标

### 背景

dailylog 目前通过 10 分钟截屏 + 视觉模型分析记录工作时间线，时间线记录中虽包含视觉模型识别的应用名（`apps` 字段），但存在以下不足：

- 10 分钟粒度，时长统计粗糙
- 视觉模型识别应用名不可靠（小窗口、非主流应用易漏）
- 没有专门面向"每个应用用了多久"的展示

### 目标

让用户知道**每天/每周/每月在哪些应用上花了多少时间**，精度达到分钟级，且不引入常驻进程、不影响日常使用性能。

### 非目标（第一版不做）

- 不追踪"后台运行"的应用，只统计前台活跃应用
- 不做应用名称映射美化（直接显示进程名）
- 日报/周报不引用应用时长数据
- 不做跨设备统计

## 2. 用户故事

- 作为用户，我想知道今天在 VS Code 上实际花了多久，以评估专注度
- 作为用户，我想按月查看各应用时长占比，了解时间去向
- 作为用户，我不想因为统计功能让电脑变卡，也不想隐私被过度采集

## 3. 方案概述

采用**前台窗口采样**：新增轻量采集脚本，由 Windows 任务计划每 2 分钟驱动一次（进程启动 → 读取前台窗口 → 追加一行数据 → 退出），不常驻内存。统计结果在桌面应用新增「应用时长统计」导航页展示。

## 4. 功能需求

### FR1 前台窗口采样

- 新增任务计划 `DailyLogUsage`，每 2 分钟执行一次采集脚本（复用现有任务计划注册/管理机制，开发期 `pythonw usage.py`，打包版 `dailylog.exe --usage`）
- 采集内容：通过 Windows API（`GetForegroundWindow` + `GetWindowProcessId` + 进程名）获取**当前前台应用进程名**（如 `chrome.exe`、`Code.exe`）
- 采样记录写入 `records/usage/YYYY-MM-DD.jsonl`，每行一条：`{"ts": "2026-08-05T09:10:00", "app": "chrome.exe"}`

### FR2 空闲排除

- 沿用现有空闲检测（`GetLastInputInfo`，阈值取设置项 `idle_minutes`，默认 5 分钟）：空闲超阈值时跳过本次采样，不写数据
- 人不在电脑前的时间不计入任何应用时长

### FR3 隐私边界

- **只记录进程名，不记录窗口标题**（窗口标题可能含文档名、网页标题等敏感信息）
- 数据仅存本机 `records/usage/`，随 `retention_days` 清理规则一并删除
- 与截屏链路（云端视觉分析）完全独立，本功能无任何网络请求

### FR4 「应用时长统计」导航页

- 桌面应用导航栏新增「应用时长统计」页（与现有「时间线」页并列）
- 支持日 / 周 / 月切换查看，日期口径与时间线页一致（周 = ISO 周，月 = 自然月）
- 展示内容：
  - 各应用时长排行（时长降序），每项显示时长与占比
  - 时长条形占比图（无第三方图表库，用 CSS 实现）
- 时长计算：`采样次数 × 2 分钟` 估算；当天实时累计，历史按文件聚合
- 空数据（当日无采样）时显示空态提示

### FR5 设置项

- 设置页新增「应用时长统计」开关（默认开启），关闭时：
  - 删除/停用 `DailyLogUsage` 任务计划
  - UI 不再展示统计数据
- 开关状态持久化到 `settings.json`（如 `usage_enabled`）

### FR6 数据生命周期

- `retention_days` 清理逻辑扩展覆盖 `records/usage/` 目录（过期同删）
- 打包脚本 build.bat 排除清单加入 `usage/`（运行时数据不进安装包）
- 数据量为一天约 720 行、几 KB，无需压缩/归档机制

## 5. 非功能需求

| 项 | 要求 |
|----|------|
| 性能 | 采集进程瞬时运行（1~2 秒），不常驻，峰值内存约 30~50MB 且即用即释放；用户日常使用无感知 |
| 可靠性 | 采样失败（API 调用失败等）记日志 `dailylog.log` 并跳过该次，不中断后续采样 |
| 兼容性 | Windows 10/11，Python 3.10+，复用现有 pywin32 / ctypes 能力，不新增第三方依赖 |

## 6. 数据设计

### 存储

```
records/usage/YYYY-MM-DD.jsonl
```

每行一条 JSON（追加写入，UTF-8）：

```json
{"ts": "2026-08-05T09:10:00", "app": "chrome.exe"}
{"ts": "2026-08-05T09:12:00", "app": "code.exe"}
```

- `ts`：采样时间，ISO 8601（本地时间）
- `app`：前台应用进程名，**统一小写并保留 `.exe` 后缀**（如 `chrome.exe`、`code.exe`），聚合按此归一，避免大小写导致同一应用被拆成两条

### 聚合口径

- 当日时长(app) = 当日该 app 采样次数 × 2 分钟
- 总时长 = 所有 app 时长之和
- 占比(app) = 当日时长(app) / 总时长
- 周/月聚合 = 范围内各日之和

## 7. 验收标准

1. 注册任务计划后，每 2 分钟 `records/usage/` 下产生当日文件并追加记录；前台窗口切换后，新采样点的 `app` 随之变化
2. 鼠标空闲超过 `idle_minutes` 期间无新采样记录
3. 应用「应用时长统计」页可切换日/周/月，时长与按文件手工计算的估算值一致（±2 分钟）
4. 关闭开关后任务计划被停用，页面显示空态；重新开启后恢复采集
5. 设置 `retention_days = 7` 时，超过 7 天的 `records/usage/` 文件被清理
6. 打开任务管理器观察：无 dailylog 相关常驻进程
7. 运行期间 `dailylog.log` 无未处理异常堆栈

## 8. 风险与说明

| 风险 | 说明与对策 |
|------|-----------|
| 进程名 ≠ 用户认知的应用名 | 第一版直接展示进程名；如需友好名称，后续加映射表（`Code.exe → VS Code`） |
| 任务计划最小粒度限制 | 任务计划 schema 最小 1 分钟，2 分钟间隔可行；如需秒级需应用进程驱动（不做） |
| 全屏应用/游戏窗口采样 | `GetForegroundWindow` 对独占全屏游戏可能返回异常值，表现为某应用时长偏高或缺失，属已知边界，可后续优化 |
| 时长精度 | 2 分钟采样为估算口径，与项目现有"按记录间隔估算"保持一致，非精确计量 |
